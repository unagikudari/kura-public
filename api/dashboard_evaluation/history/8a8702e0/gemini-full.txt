### 各基準の詳細とエビデンス

#### 1. `situation`（状況が一目で分かる）: **partial**
* **できている点**:
  * 最上部に人のアクションが必要な「あなたへの確認依頼（`smegma · 新候補の評価` 判定済み 0 / 341枚）」が配置されている。
  * その直下に「本番と改善処理」があり、本番稼働中（`release 15`）、停止中（機械による付与停止 4タグ）、稼働中（`smegma の実験` 13/16工程）、未確認（自動学習の履歴）が区別されている。
* **課題**:
  * 画面上部に「詳細集計を再読み込み」（親ドキュメント）、「判定数を更新」（確認依頼セクション）、「状況を更新」（本番と改善処理セクション）の3つの更新ボタンが並び、どれを押せば何が更新されるのか直感的に分かりにくい。
  * 実験行のステータスが「未公開 · 機械による候補の採点 · nodeb CPU · 本番と同じ6GiB枠で検証 · 13/16 工程」となっており、採点なのかリソース検証なのかが一目で判別しづらい。

#### 2. `consistency`（矛盾がない）: **partial**
* **できている点**:
  * 候補評価（`未公開`、341枚確認待ち）と本番使用（`release 15`、`smegma` 含む4タグの機械付与停止）が明確に分離されている。
  * 完了フェーズのラベルが `completed: 'この実験は完了・品質は未承認'` と定義されており、実験完了を全体のアイドルや品質合格と誤認させない。
* **課題**:
  * Runtime コンポーネントの `labels` マップが `evaluating: '機械による候補の採点'` に固定されているため、実際には7000件の採点が終わり、オフラインで nodeb CPU（6GiB枠）のパイプライン・リソース検証（13/16工程）が動いている状態でも「機械による候補の採点」と表示され、隣の説明（「本番と同じ6GiB枠で検証」）と意味が食い違っている。

#### 3. `duplication`（重複がない）: **partial**
* **できている点**:
  * 固定確認セットと境界セットの重複について「境界セットは固定確認セットと重複します。件数は合計しません。」と明記し、合算による誤解を防いでいる。
  * 比較グラフを `<details>` 内に格納し、`compact` モード時は見出しや重複テキストを省略している。
* **課題**:
  * 現在対応が必要な `smegma`（新候補の評価・341枚）が、上部の「あなたへの確認依頼」と下部の「確認セットの一覧」テーブル1行目の**2箇所に重複表示**されており、アクションリンクも「この341枚を確認」と「未判定の341枚へ」の2つが存在する。

#### 4. `completeness`（必要な情報が揃う）: **partial**
* **できている点**:
  * 確認依頼の対象（`smegma`）、残り枚数（341枚）、担当（あなた）、次の処理（基準照合と改善・配備前審査）が同じセクション内で完結している。
* **課題**:
  * `smegma` 341枚の「比較はまだ表示しません」について、**「判定への先入観（バイアス）を防ぐため、完了まで予測スコア・比較を非表示にしている」という理由**が書かれていない。また、341枚が「固定159枚＋拡張182枚」で構成されている背景も不明。
  * 「機械による付与停止」の行では、初期表示で「4タグ: ...」としか出ず、なぜ止まっているか・どうすれば解除されるか（「解除には修正版の品質確認が必要です」）を知るには `<details>停止の理由</details>` を開く必要がある。

#### 5. `brevity`（初期表示が少なく明確）: **partial**
* **できている点**:
  * モデルSHA・閾値・スコアSHA（「採点情報を開く」）や比較グラフ、集計と公開のルールは `<details>` に折りたたまれている。
* **課題**:
  * 任意の確認セット（`horse_penis` 263枚、`smegma` 固定140枚、`knotted_penis` 30枚、受領済み8枚）を含む「確認セットの一覧」テーブル全体が初期表示で展開されており、現在の最優先タスク（341枚の確認）以外の情報量が多い。

#### 6. `actionability`（次の行動が具体的）: **pass**
* **根拠**:
  * 誰が（あなたの確認待ち）、何を（`smegma · 新候補の評価` の未判定341枚）、どうするか（「この341枚を確認」リンク、分からない画像は残してよい旨）、揃うとどうなるか（「判定が揃うと、次は基準照合と改善・配備前審査です」）がファーストビューで迷わず把握できる。

#### 7. `exploration`（比較・探索ができる）: **partial**
* **できている点**:
  * 表示フィルター（全セット / 確認依頼 / 不一致あり / 未判定あり）、タグ名検索（`type="search"`）、並び順セレクト、件数表示（`5/5セット`）、条件変更時のみ現れる「表示をリセット」ボタンが実装されている。
* **課題（ソート不具合）**:
  * `visible` の `.sort()` 実装において：
    ```ts
    .sort((a,b) => (sort==='tag' ? 0 : sort==='remaining' ? b.remaining-a.remaining : sort==='disagreement' ? (difference(b)??-1)-(difference(a)??-1) : Number(requested(b))-Number(requested(a)) || b.remaining-a.remaining) || a.tag.localeCompare(b.tag) || a.queue_sha256.localeCompare(b.queue_sha256))
    ```
    JavaScript の論理 OR（`||`）は左辺が `0` の場合に右辺を評価するため、`sort === 'tag'` のときに三項演算子が `0` を返すと、そのままデフォルトの `Number(requested(b))-Number(requested(a)) || b.remaining-a.remaining` が実行される。結果として**「タグ名順」を選択してもタグ名順にならず、「依頼を先頭・未判定が多い順」のままになるバグ**がある。

#### 8. `graphics`（図が判断を助ける）: **partial**
* **できている点**:
  * 確認依頼のプログレスバーは `value={q.total-q.remaining} max={q.total}` で「判定済み 0 / 341枚」と枚数進捗であることを明示し、品質スコアと混同させない。
  * 新候補評価（341枚）では予測比較グラフを出さず、既存の任意確認セットのみ `<details>比較グラフ</details>` で内訳（ありで一致 / なしで一致 / モデルだけが「あり」 / 人だけが「あり」 / 未比較）と枚数を表示している。
  * `knotted_penis`（30枚）は「未測定」と表示し、0や合格扱いにしていない。
* **課題**:
  * 視覚的なバーの配色・幅・凡例の読みやすさはスクリーンショット不在のため未検証。
  * 実験進捗の `<progress value={x.done} max={x.total} aria-label="実験内の工程数">` は、確認依頼側の `<progress>` と比べてラベルが汎用的で、どのタグの何工程か（13/16工程）が属性値に含まれていない。

#### 9. `freshness`（鮮度と不確実性が分かる）: **partial**
* **できている点**:
  * `experimentLive` と `snapshotOld`（120秒閾値）により、古い実験報告や学習履歴には自動的に `最後の報告: …（過去）・現在の稼働は未確認` が付与され、現在稼働中と誤認させない（「自動学習の履歴」で実際に機能している）。
  * API 取得失敗時には `確認依頼を取得できません。「作業なし」とは判断できません。` と表示し、空状態と通信失敗を厳密に区別している。
* **課題**:
  * 確認依頼セクションには取得時刻が表示されず、ページ最下部の `最終取得 2026/11/17 3:33:22（この端末の時刻）` まで目を動かす必要がある。
  * 「本番と改善処理」の実験・学習の観測時刻（5分周期のバックグラウンド観測によるタイムスタンプ）と、画面自身の最終取得時刻（30秒周期）の関係が初見では分かりにくい。

#### 10. `accessibility`（操作しやすい）: **unverified**
* **コードから確認できる配慮**:
  * インタラクティブ要素（`button`, `input`, `select`, `a`, `summary`）に `min-height: 44px` が指定されている。
  * 比較グラフの凡例は色チップだけでなくテキストと枚数（`{p.label} {p.value}枚`）を併記している。
* **未検証・懸念点**:
  * 実機スクリーンショット（390px / 1280px）がないため、実際のタップターゲット間隔、横スクロール有無、配色コントラストは **unverified**。
  * 700px 以下で `table, tbody, tr, th, td { display: block }` に変換する際、HTML 側に明示的な `role="table"`, `role="row"`, `role="cell"` がハードコードされているため、CSS レイアウトと ARIA テーブル構造の不整合がスクリーンリーダー利用時に影響する可能性がある。

### 改善の優先順位と「次にやるべき最小の1改善」

#### 優先順位リスト
1. **【最優先・最小改善】「タグ名順」ソートが機能しない論理演算子バグの修正と、341枚セットの「比較非表示」理由（先入観防止）の明記**（`exploration` / `completeness`）
2. **実験フェーズ表示の精緻化**：`evaluating` を一律「機械による候補の採点」とせず、採点完了後の6GiB枠パイプライン検証（13/16工程）であることが矛盾なく伝わるラベルにする（`consistency` / `situation`）
3. **初期表示の整理（重複・情報量の削減）**：任意の確認セット一覧（または確認依頼と重複する行）を整理し、確認依頼の取得時刻を上部に近づける（`duplication` / `brevity` / `freshness`）

#### 推奨する次の1改善（Next Small Improvement）

過剰な作り込み（perfection loop）を避け、最小のコード変更でユーザーの操作裏切り（ソート不能）と疑問（なぜ比較が出ないのか）を同時に解消するため、**確認セット一覧の `sort === 'tag'` バグ修正＋新候補評価の比較非表示理由の補足**を推奨します。

* **ユーザーメリット**:
  1. 「並び順: タグ名順」を選んだ際に、期待通りタグのアルファベット順（`horse_penis` → `knotted_penis` → `smegma`）で並ぶようになる。
  2. `smegma`（新候補の評価・341枚）の比較欄で、単なる「比較はまだ表示しません」ではなく「先入観を防ぐため完了まで非表示」と分かり、システム不具合や未計算ではないことが一目で理解できる。

* **具体的な変更箇所（対象1ファイル・2箇所のみ）**:

```ts
// 1. visible のソート条件: sort === 'tag' のときに a.tag.localeCompare(b.tag) を直接返すよう修正
const visible = $derived(
  (queues ?? [])
    .filter(q =>
      q.tag.toLowerCase().includes(search.trim().toLowerCase()) &&
      (filter === 'all' ||
        (filter === 'requests' && requested(q)) ||
        (filter === 'remaining' && q.remaining > 0) ||
        (filter === 'disagreement' && (difference(q) ?? 0) > 0))
    )
    .sort((a, b) =>
      (sort === 'tag'
        ? a.tag.localeCompare(b.tag)
        : sort === 'remaining'
          ? b.remaining - a.remaining
          : sort === 'disagreement'
            ? (difference(b) ?? -1) - (difference(a) ?? -1)
            : Number(requested(b)) - Number(requested(a)) || b.remaining - a.remaining) ||
      a.tag.localeCompare(b.tag) ||
      a.queue_sha256.localeCompare(b.queue_sha256)
    )
);
```
