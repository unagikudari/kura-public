## 各基準の詳細評価と根拠

### 1. `situation`（状況が一目で分かる）：**partial**
* **達成できている点**:
  * 最上部に `あなたへの確認依頼` → `あなたの確認待ち: smegma · 新候補の評価` → `この341枚を確認` が配置されており、「人間がいま対応すべき最優先事項」はファーストビューで分かる。
  * `機械による付与停止`（4タグ）と `本番の選択`（`release 15`）が明示されている。
* **問題点（Evidence）**:
  * `smegma の改善` が `未公開 · 最後の報告: 実験完了・品質未承認（過去）・現在の稼働は未確認`、`自動学習の最終報告` が `smegma · 最後の報告: 評価履歴を登録済み（過去）・現在の稼働は未確認` となっており、「正常に完了して次の人手確認（341枚）を待っている状態」なのか「プロセスが異常停止して監視が途絶えている状態」なのかが一目で区別できない。
  * バックグラウンドで5分ごとに動く読み取り専用オブザーバー（human observer）が実際に稼働していることや、7,000枚の採点が完了済みであることが画面から読み取れない。

### 2. `consistency`（矛盾がない）：**pass**
* **達成できている点（Evidence）**:
  * 本番採用中モデル（`本番の選択: release 15`）、本番での自動付与停止（`機械による付与停止: 4タグ ... smegma`）、新候補の評価待ち（`未公開` / `新候補の評価 · 確認依頼` / `341枚`）が明確に分離されている。
  * 新候補341枚についてはバイアス防止のため予測スコアを伏せ、一覧でも `比較はまだ表示しません` と一貫してブラインド状態を保っている。
  * 固定確認セット（`smegma` 300枚中140枚未判定）と判定境界セット（`smegma` 8枚受領済み）の重複についても、`境界セットは固定確認セットと重複します。件数は合計しません。` と明記して件数矛盾を防いでいる。

### 3. `duplication`（重複がない）：**partial**
* **問題点（Evidence）**:

  2. **更新ボタンの三重分散**: 親画面の `詳細集計を再読み込み`、確認依頼セクションの `判定数を更新`、本番と改善処理セクションの `状況を更新` の3つの更新ボタンが並び、どれを押せば何が更新されるのか（特に「詳細集計を再読み込み」と他の2つの関係）が重複・競合している。

### 4. `completeness`（必要な情報が揃う）：**partial**
* **達成できている点**:
  * 5つの確認セットすべての対象タグ・用途・未判定枚数/全枚数・操作リンク・観測/取得時刻が表示されている。
* **問題点（Evidence）**:
  * **「何が揃えばどう進むか（次の処理と担当）」の欠落**: `判定できた画像を集計します。未判定が残る間は全体の品質を確定しません。` と否定形（〜しません）でしか書かれておらず、「全341枚の判定が完了すると（または5分ごとの自動観測で集計されると）候補評価が確定し、停止解除や公開判断に進める」という前向きなパイプラインの繋がりが同じ場所で分からない。
  * **341枚の性質の欠落**: なぜ341枚なのか（固定159枚＋拡張182枚であり、既存判定の流用ではなく全枚に新規の明示ラベルが必要であること）が画面から分からないため、下部の `smegma 固定確認セット（160枚比較済み・140枚未判定）` を見て「なぜ既に160枚判定したのに新候補は341枚中0枚判定なのか？」と疑問を抱かせる。

### 5. `brevity`（初期表示が少なく明確）：**partial**
* **達成できている点**:
  * 停止の理由、各セットの比較グラフ、モデルSHA256・スコアSHA256・閾値（`採点情報を開く`）がすべて `<details>` の中に隠されており、初期表示から内部ハッシュ等は排除されている。
* **問題点（Evidence）**:
  * **注意書き（`.note`）の過多**:
    1. `判定できた画像を集計します。未判定が残る間は全体の品質を確定しません。`
    2. `分からない画像は判定せず残して構いません。未判定を「なし」には数えません。判定が揃っても品質合格や自動公開を意味しません。`
    3. `境界セットは固定確認セットと重複します。件数は合計しません。`
    4. `不一致は人の誤りとは限りません。比較は固定モデルと現在の人手判定によるもので、学習の進捗・全画像の精度・公開の合否ではありません。`
    5. `最終取得 2026/11/17 2:39:49（この端末の時刻）`
    これらが常時展開されており、「〜しません」「〜ではありません」という防御的説明が画面のかなりの面積を占めている。
  * **任意セット一覧の常時全展開**: 今やるべき作業は `smegma` の341枚だけなのに、任意確認の3セットや受領済みの1セットを含むフルテーブル＋フィルターUIが最初からすべて展開されている。

### 6. `actionability`（次の行動が具体的）：**partial**
* **達成できている点**:
  * 最優先アクション `この341枚を確認`（`.primary` リンク）と、一覧の各行にある `未判定のN枚へ` / `未判定のN枚を確認（任意）` / `不一致N枚` のリンクが明確に分かれている。
* **問題点（Evidence）**:
  * **完了条件と保留時の扱いの曖昧さ**: 「分からない画像は判定せず残して構いません」とある一方で、「未判定が残る間は全体の品質を確定しません」とあるため、**分からない画像を1枚でも残したら永久に品質確定（次工程）に進めないのか、それともどうすればよいのか**が行動指針として矛盾・宙吊りになっている。
  * 判定後に人間が `判定数を更新` を押す必要があるのか、5分周期のバックグラウンド処理が自動で拾うのかも明示されていない。

### 7. `exploration`（比較・探索ができる）：**partial**
* **達成できている点**:
  * 表示フィルター（`全セット` / `確認依頼` / `不一致あり` / `未判定あり`）、タグ名検索（`type="search"`）、並び順（`依頼を先頭` / `未判定が多い順` / `不一致が多い順` / `タグ名順`）、件数表示（`5/5セット`）、条件変更時の `表示をリセット` ボタンが実装されている。
* **問題点（Evidence）**:
  * ソート式の実装：
    ```ts
    (sort==='tag' ? 0 : sort==='remaining' ? b.remaining-a.remaining : sort==='disagreement' ? (difference(b)??-1)-(difference(a)??-1) : Number(requested(b))-Number(requested(a)) || b.remaining-a.remaining) || a.tag.localeCompare(b.tag) || a.queue_sha256.localeCompare(b.queue_sha256)
    ```
    `sort === 'tag'` のときに三項演算子が `0` を返し、フォールバックの `|| a.tag.localeCompare(b.tag)` に頼るトリッキーな構造になっている（同一タグ `smegma` が3セットあるため、タグ名順の次順位が `queue_sha256` というランダムなハッシュ順になり、用途や未判定数順にならない）。
  * フィルターに「受領済み（完了済み）」や「比較あり」がなく、`不一致が多い順` でソートした際に「比較未表示（新候補341枚）」と「未測定（knotted_penis 30枚）」がどちらも `difference(q) === null`（`-1`）として同列末尾になる。

### 8. `graphics`（図が判断を助ける）：**partial**
* **達成できている点（Evidence）**:
  * `ReviewComparison.svelte` では、`validComparison` を満たす3セット（`horse_penis`, `smegma` 固定, `smegma` 境界）のみ `<details><summary>比較グラフ</summary>` を表示し、`smegma` 新候補（341枚・盲検）は `比較はまだ表示しません`、`knotted_penis`（30枚）は `未測定` としてグラフ自体を出さないことで、未測定や未判定を「0%」や「精度0」と誤認させない設計になっている。
  * 内訳も `ありで一致` / `なしで一致` / `モデルだけが「あり」` / `人だけが「あり」` / `未比較` の**枚数（件数）**で統一され、母集団の精度や学習進捗と混同しないよう注意書きが付いている。
* **問題点・未検証点（Evidence）**:
  * スクリーンショットがないため、`.bar`（高さ16pxのflexバー）の実際の見え方は **unverified**。
  * コード上、内訳の0枚の項目（例：`horse_penis` の不一致0枚など）も `<ul>{#each parts as p}` で全5項目が出力され、かつ `.bar` と `<li>` の凡例が単色背景（`#278265`, `#648e80`, `#c85c29`, `#8b65bc`, `#8a8a8a`）のみに依存している（テキスト併記はあるが、バー自体は色のみで区切り線やハッチングがない）。

### 9. `freshness`（鮮度と不確実性が分かる）：**partial**
* **達成できている点（Evidence）**:
  * Runtimeコンポーネントで `experimentLive`（`fresh && age_seconds + 経過 <= 120`）と `snapshotOld`（120秒超）を判定し、古い場合は `最後の報告: ...（過去）・現在の稼働は未確認` と表示して現在進行中と誤認させない。
  * 各報告に `観測 2026/11/17 2:30:20`、`観測 2026/11/17 1:15:13` と個別の観測時刻が表示されている。
* **問題点（Evidence）**:
  * 確認セット一覧の `最終取得 2026/11/17 2:39:49（この端末の時刻）` は、`fetchedAt = new Date().toLocaleString('ja-JP')` でクライアントがAPIレスポンスを受け取った時刻を表示しているだけであり、**バックエンドの判定数集計（5分間隔のhuman observer等）がいつ時点のDB状態を反映しているのか**が分からない。「判定数を更新」を押して時刻が新しくなっても、裏の集計が5分前のままならユーザーは「さっき判定したのに減っていない」と混乱する。

### 10. `accessibility`（操作しやすい）：**unverified**（コード上の課題あり）
* **未検証（Unverified）**:
  * スクリーンショット（390px / 1280px）および実機操作がないため、実際のフォーカスリング視認性、モバイルでの横スクロール有無、カラーコントラスト比は **unverified**。
* **コードから確認できる良い点と問題点（Evidence）**:
  * 良い点：`button, input, select, summary, a` に `min-height: 44px` が指定されており、タップターゲットサイズの基準を配慮している。バー自体は `aria-hidden="true"` とし、直後の `<ul>` で項目名と枚数をテキストで読ませている。
  * **問題点1（レスポンシブ表のARIA破綻）**: `@media(max-width:700px)` で `table, tbody, tr, th, td { display: block }` に変更しているが、HTML側に明示的な `role="table"`, `role="rowgroup"`, `role="row"`, `role="cell"`, `role="columnheader"`, `role="rowheader"` がハードコードされている。またモバイル時に `<tr class="details-row"><td colspan="4">` がブロック化されると、前後の行との境界やラベルが曖昧になる。
  * **問題点2（状態通知）**: `状況を更新` ボタンには `aria-disabled={busy}` がなく（`判定数を更新` には `aria-busy={loading} aria-disabled={loading}` の両方がある）、更新完了時のスクリーンリーダー向けフィードバックも一貫していない。

## 次に実装すべき「1つの小さな改善」（Next Small Improvement）

完璧主義ループ（perfection loop）を避け、最小の変更でユーザーの迷い（「なぜ固定セットで160枚判定済みなのに341枚全部が未判定なのか？」「341枚判定したら何が起きるのか？」「分からない画像を残したら止まるのか？」）を解消し、初期表示のテキスト負荷を下げるため、**「あなたへの確認依頼」セクションの文言・構造の1点改修**を提案します。

### 変更内容（対象：確認依頼セクション `.request-section`）
1. **散在する2つの `.note`（計4文の否定形説明）を1つの簡潔なステータス＆行動ガイドに統合**し、以下を明記する：
   * **対象の意味**: 新候補の評価には、専用の341枚（固定159枚＋拡張182枚）すべてに新しい判定が必要であること（予測スコアは偏り防止のため非表示）。
   * **次の行動と進行条件**: 全341枚を（「あり」「なし」または「分からない（保留）」として）確認し終えると集計が確定し、公開・停止解除の判断に進めること（または保留画像の具体的な扱い）。
2. **詳細ルール（未判定の扱い・自動公開されない旨など）は `<details><summary>判定と集計のルール</summary>` に折りたたむ**ことで、初期表示の文字数を半減させる。
