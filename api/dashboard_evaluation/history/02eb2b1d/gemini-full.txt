#### 2. `consistency` — 矛盾がない
*条件: 候補評価と本番使用を別に示し、同じ状態を矛盾して説明しない*
- **Rating:** **`partial`**
- **Evidence:**
  - **Strengths:** Candidate evaluation (`smegma の改善: 未公開 · 検証`, `新候補の評価 · 確認依頼 159/159枚`) is separated from production (`本番の選択 release 15`), and disclaimers state that comparisons do not reflect training progress, full-population accuracy, or publication approval.
  - **Contradictions / Confusions:**
    1. For `smegma`, the runtime section says `未公開 · 検証 · 108/5000 工程` (`labels['evaluating'] = '検証'`), while the review table also says `smegma 新候補の評価 · 確認依頼 159/159枚`. Both use evaluation terminology (`検証` vs `新候補の評価`) without distinguishing that `108/5000 工程` is machine CPU scoring on `nodeb + p52` (5,000 images) whereas `159/159枚` is an unjudged human sample (9 pred-positive + 150 pred-negative from unseen 2,000, scores hidden).
    2. When `smegma 新候補の評価` (`159/159枚`) has `comparison.state === 'not_supplied'` (scores intentionally withheld to avoid bias), the table cell says `未測定`, while expanding `比較グラフ・全画像` says `比較スコアは未用意です。` — two different terms for the same intentional blind-review state, neither explaining that scores are intentionally hidden during candidate human evaluation to prevent bias.
- **Feasible Improvement (Priority: High):** Distinguish machine scoring (`検証採点中 108/5000`) from human blind evaluation, and replace `未測定` / `比較スコアは未用意です。` on `candidate_evaluation` queues with explicit blind-evaluation wording (e.g., `採点非表示（判定バイアス防止）`).

#### 4. `completeness` — 必要な情報が揃う
*条件: 対象・状態・理由・担当・次の処理・最終更新が同じ場所で分かる*
- **Rating:** **`partial`**
- **Evidence:**
  - **Present:** Target tag (`smegma`, `horse_penis`, `knotted_penis`), count (`159/159枚`, `108/5000 工程`), host (`nodeb + p52 (CPU 8 each)`), and timestamps (`観測 2026/11/17 1:39:29`, `1:15:13`, `最終取得 2026/11/17 1:39:49`) are shown.
  - **Missing / Incomplete in the same place:**
    1. **Sampling rationale / reason (`理由`):** For `smegma 新候補の評価 159/159枚`, there is no explanation of *why* these 159 images were selected (9 predicted-positive + 150 predicted-negative sample from 2,000 unseen images, with labels/scores withheld to avoid bias) or what happens once all 159 are judged.
    2. **Owner / actor (`担当`) & Next step (`次の処理`):** In `本番と改善処理`, `smegma の改善` (`108/5000 工程`) and `自動学習の最終報告` (`現在の稼働は未確認`) do not state who/what is responsible next (system vs. human) or whether the 159-image human review or the 5,000-image CPU scoring is the gate for the next lifecycle transition.

- **Feasible Improvement (Priority: High):** Add a concise queue reason/gate note or API-driven description to requested queues (e.g., explaining that the 159 images are an unseen candidate evaluation sample with scores hidden, and that completing them unlocks candidate quality evaluation).

#### 9. `freshness` — 鮮度と不確実性が分かる
*条件: 古い報告や理由未記録を現在の実行と誤認しない*
- **Rating:** **`pass`**
- **Evidence:**
  - `RuntimeSummary` tracks both server-reported `fresh` / `age_seconds` and client elapsed time (`clock - receivedAt`), degrading `experiment` to `最後の報告: ...（過去）・現在の稼働は未確認` after 120s and hiding the `<progress>` bar so stale progress is never shown as actively running.
  - `自動学習の最終報告` explicitly renders `smegma · 最後の報告: 評価履歴を登録済み（過去）・現在の稼働は未確認` with `観測 2026/11/17 1:15:13` (~25 minutes older than current time `1:40:13`), preventing confusion with the live `1:39:29` experiment observation.
  - Fetch failures in both components explicitly warn that lack of data does not mean "no work" (`確認依頼を取得できません。「作業なし」とは判断できません。`) and flag stale snapshots (`以下は前回取得した状態です。`).
- **Feasible Improvement (Priority: Low):** Display relative age (e.g., `25分前`) next to raw timestamps (`2026/11/17 1:15:13`) so the user does not have to mentally compare `1:15:13` against `1:39:29` to spot the 24-minute gap.

#### 10. `accessibility` — 操作しやすい
*条件: スマホ・キーボードで操作でき、色だけに意味を持たせない*
- **Rating:** **`unverified`** (static code **`partial`**)
- **Evidence:**
  - **Static Code Strengths:** Interactive elements (`button`, `input`, `select`, `a`, `summary`) set `min-height: 44px`. The stacked bar is `aria-hidden="true"` and paired with an explicit text/count `<ul>` list (`ありで一致 X枚`, etc.), so meaning does not rely on color alone. Mobile CSS (`@media(max-width:700px)`) switches table cells to block layout with `td[data-label]::before`.
  - **Code Defect & Unverified Visuals:**
    1. On mobile (`@media(max-width:700px)`), `table, tbody, tr, th, td { display: block }` is applied while explicit `<table role="table">`, `<tr role="row">`, `<th role="rowheader">`, and `<td role="cell">` ARIA attributes are hardcoded in the markup. This is a good pattern for preserving table semantics in CSS block layout, **but** `.details-row td` has no `data-label` and `th, td { padding: 4px 0 }` may stack tightly; actual mobile layout, keyboard focus ring visibility, and touch overflow cannot be verified without screenshots (`unverified`).
    2. `ReviewQueues` does not pause its 30s `setInterval` polling when `document.hidden` is true (unlike `RuntimeSummary`), which can reset/announce live regions while backgrounded.
- **Feasible Improvement (Priority: Low):** Redundant explicit ARIA roles (`role="table"`, `role="row"`, `role="cell"`) can be kept, but guard `ReviewQueues` auto-refresh with `!document.hidden` (matching `RuntimeSummary`) and avoid resetting `<details open>` state when the 30-second background poll updates `queues`.
