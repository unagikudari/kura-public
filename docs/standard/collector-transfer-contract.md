# コレクション取り込み・書き出し契約

- **Status:** Draft / 実装契約案。API・UI・MCPの提供開始を意味しない。
- **Version:** 0.1.0
- **Date:** 2026-10-18
- **Scope:** [製品仕様](./collector-product-profile.md) §3–5、§8の第1段階。

## 1. 境界と最初の実装範囲

最初の実装は「ローカル原本をコピーして取り込む」「選択した原本をメタデータと
一緒に書き出す」「同じ書き出しを再取り込みする」を一往復で成立させる。
元の場所を参照する管理、類似画像の統合、クラウド同期は後続とする。
UIのドロップ、ファイル選択、MCPは同じ計画・実行サービスを呼ぶ。

本書は既存8巻・ADRを上書きしない。原本の同一性はメディア上の事実、
タグの意味的な現在値はResolverによる投影である。交換用JSONは外部への
スナップショットであり、正本のJSON保存やDBへの直接書き戻しを認めない。

## 2. 操作単位と永続化

| 単位 | 役割・一意性 |
|---|---|
| operation | ユーザーの1回の取り込み／書き出し。再接続後も同じIDで参照する |
| item | 入力内の1つの出現位置。operation内の安定キーで識別する |
| original | SHA256とバイト数で検証した原本。名前・順序から独立する |
| occurrence | 作品内の1つの位置。同じ原本が複数位置に現れることを許す |
| attempt | itemの処理試行。元のitemと試行回数を保持し、新規itemに作り直さない |

operation、item、attempt、作品内位置、入力根拠は関係テーブルで永続化する。
この段階ではDDLを確定しない。[目標構造](./collector-target-architecture.md)として
独立にキー・制約・仕事量を設計する。既存の取り込みキュー・ファイル表、`post`、
`pool_post` の対応と互換移行は別に定義し、新モデルの構造をそれらに従属させない。
既存の取り込みキューの状態値は互換APIに残し、共通状態への対応をアダプターで提供する。

計画は対象・順序・保存方法・判明した件数／容量・競合を返す。
未知の容量はnullとし、0にしない。計画には版と有効期限を持たせ、実行時に
変更された入力を再検証する。期限切れや対象変更を黙って別の計画として実行しない。
ファイルの列挙・全件ハッシュ計算も長時間処理になり得るため、計画の作成自体を
非同期で行え、途中の計画から検証済みitemを処理できる構造とする。

## 3. 共通ジョブ状態

| 状態 | 意味 |
|---|---|
| pending | 受付済み。待機理由と、再開時刻が判明していればそれを返す |
| running | リース所有者が処理中。段階と最終進捗時刻を返す |
| paused | 明示的に停止中。進行中の安全な処理境界までの遅延を許す |
| needs_attention | 自動回復できない入力・保存先・検証エラー。理由と回復操作を返す |
| succeeded | 列挙確定、全itemが成功、必須メタデータの確定まで完了 |
| partial | 列挙確定、成功と最終失敗が混在し、自動処理が残っていない |
| failed | 自動処理が残らず成功itemもない。空入力は `empty_selection` として区別する |
| cancelled | 取消済み。既に確定した成果物は結果に残す |

基本遷移はpending→running→終端。runningからpending（期限付き再試行）、
paused、needs_attentionへ遷移できる。paused／needs_attentionからの再開は
同じoperationへ戻す。終端からの再試行もitem履歴を引き継ぎ、過去の結果を保存する。
取消要求後は新しいitemをclaimしない。停止できないファイル処理は安全な境界まで
終え、その成果物を記録してからcancelledとする。

親の列挙終了と取得完了を分ける。`enumeration_complete=true` でも子がpendingなら
親はsucceededではない。`ogachan97` のような一覧展開は「探索済み69・取得待ち69」と
示せる必要がある。既存親taskのcompletedを取得成功と読み替えない。

進捗応答は状態、段階、列挙確定、既知item数、成功／重複再利用／失敗／待機／実行中／
取消数、転送バイト、最終進捗時刻、待機理由、可能な操作を含む。
成功と重複再利用の件数は排他的に数える。未知総数の進捗率はnull。
派生生成・タグ付けは別の子処理として示し、原本登録成功を取り消さない。

## 4. 原本確定と再開

取り込みは次の順序を守る。

1. 入力を読み、管理領域の一時ファイルへコピーしながらSHA256とサイズを計算する。
2. コピー結果を検証する。読取中に入力が変わった場合は再検証または要対応とする。
3. 原本を同一ファイルシステム内の確定先へ原子的に配置し、必要な耐久化を行う。
4. DBトランザクションで原本、item受領記録、由来、必要な作品内位置を確定する。
5. 閲覧用派生物とタグ付けを別ジョブとして予約する。

DBとファイル配置は単一トランザクションではない。手順3直後の停止で残るファイルは
回収可能な未参照原本として照合する。受領記録なしに成功を返さず、ファイルが
確定していないDB参照を公開しない。照合処理はユーザー原本を削除しない。

同時投入の同一原本は、DBの一意性と競合後の再照合で同じ原本へ収束させる。
重複原本の再利用でも新しい由来・作品所属・出現位置は保存する。
SHA256が等しいのにサイズが異なる等の矛盾は要対応とし、自動上書きしない。
既存 `post.sha256` がNULLなら未検証と扱う。配信用WebPを原本としてハッシュしない。

受付の冪等キーは利用者・操作種別でスコープを分ける。同じキーと同じ要求は
同じoperationを返し、同じキーで異なる要求は競合とする。
ファイル名だけを原本またはitemの冪等キーにしない。
リースには世代を持たせ、期限切れworkerの完了報告で新workerの状態を上書きしない。

## 5. 待ち行列と資源

手動操作の子にも由来・親ID・優先度を継承する。子を無条件に最低優先度へ落とさない。
大量の子が対話操作を独占しないよう、親単位の連続claim数に上限を設ける。
バックグラウンドも有限の待ちで進める公平性を別に持ち、単純な優先度だけで放置しない。
待機時間の上限値と配分比は最低構成の負荷測定で決める。

再試行上限と「新規受領が増えない」予算はsource／itemに結び付ける。
レート制限・quotaは再開時刻付きの待機とし、その間はworker・DB接続を保持しない。
進捗は新たに確定したitem／出現位置の受領記録で数える。既存原本の再利用でも
未受領の位置が埋まれば進捗とし、受領済みの同じ位置を重複照合しただけでは
進捗なし予算を解除しない。新規原本数だけで正当な再開を停止しない。
CPU、I/O、DB接続、並列数に予算を持ち、ファイル全体をRAMへ読み込まない。

## 6. 書き出しと交換形式 v0.1案

対象と順序は計画時点のスナップショットIDで固定する。後から一覧が変化しても
ページ走査で欠落・二重取得しない。実行時に認可を再確認する。
原本が読めない場合、軽量派生物に黙って置き換えずitemを失敗として残す。

出力ディレクトリは `originals/` と `manifest.json` を持つ。manifestには次を含める。

| フィールド | 内容 |
|---|---|
| format_version | 互換性判定用の固定版。未知のmajor版は書込み前に拒否する |
| export_id / created_at | 書き出しの識別子・UTC時刻 |
| selection_snapshot | 対象・順序を固定した世代の識別子 |
| originals | パッケージ内ID、相対パス、SHA256、バイト数、媒体種別、元の名前 |
| collections | 作品ID・名前、位置IDと順序とoriginal参照。原本参照の重複を許す |
| evidence | 根拠ID、対象原本、判定元、種別、値、根拠版、元の日時、取消・訂正の参照 |
| projection | 現在タグ等の表示スナップショットとResolver版・投影世代。根拠と分離する |
| results | item別の成功／失敗、機械可読理由、未出力対象 |

同一原本は1ファイルでも作品内位置は複数保持する。原本パスはハッシュを基準に生成し、
入力名を直接パスにしない。絶対パス、`..`、シンボリックリンクによる出力先外参照を
拒否する。既存ファイルは一致を検証して再利用するか競合を返し、上書きしない。

manifestと原本を照合してから書き出しを成功とする。中断中は未完了と分かる別名で
manifestを保存し、確定時に原子的に置換する。全体が失敗しても受領済みitemを照合して
再開できる。保存先の空き容量は事前確認と実行中確認の両方を行う。

再取り込みは全参照・版・ハッシュ・サイズを検証し、入力根拠を共通サービスで登録する。
輸入された判定元はローカルのhumanとして偽装せず、元のライブラリと版を名前空間に含める。
未知の根拠形式は保全して要対応とし、現在タグをhuman根拠へ変換しない。
根拠を復元できない旧データはその制約を明示する。完全な意味情報の往復を宣言しない。
APIキー、Cookie、ローカル絶対パス、取得元の認証情報は書き出しに含めない。

## 7. UI・MCPと検収条件

共通サービスの能力はplan、start、get、list、pause、resume、cancel、retryとする。
具体的なHTTP経路・MCP名は実装段階で固定する。MCPへホスト任意パスの読書きを
公開せず、UIと同じ利用者権限の範囲に限定した保存先ID・入力ハンドルを渡す。

検収では最低限、次を実装テストで証明する。

- 同じ原本2件・異なる原本1件・同一原本の複数作品内位置を投入し、受領と位置を照合する。
- 原本確定前後、DB確定前後、manifest確定前後で停止し、再開後に欠落・二重登録がない。
- 同時再送、期限切れworker、取消と完了の競合が履歴と成果物を壊さない。
- 壊れた原本、容量不足、取り外された保存先を成功とせず、回復操作を提示する。
- export→importで原本ハッシュ・バイト数・作品順序・根拠と訂正参照を比較する。
- 列挙終了・子待機の親を完了表示せず、UIとMCPが同じ結果を返す。
- 手動子タスクが進み、バックグラウンドも飢餓せず、再試行が予算内で止まる。

交換形式のJSON Schema、根拠型のレジストリ、互換APIとの状態対応、具体的なDDLは
この契約に従う次の実装成果物とする。現時点では上記の検収は未実施。
