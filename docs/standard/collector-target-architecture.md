# コレクター向け目標アーキテクチャ

- **Status:** Draft / 次世代構造の設計案。実装済みDDL・性能保証ではない。
- **Version:** 0.1.1
- **Date:** 2026-10-22
- **方針:** 既存実装への継ぎ足しではなく、必要な仕事量から構造を設計する。

## 1. 設計の出発点

目標は、長年のコレクションを低性能PCでも保全・整理・閲覧できること。
既存 `public.post`、szurubooru由来の関連表、現在の取り込みキューを新設計の中心にしない。
既存 `database/schema.sql` も完成形ではなく、照合・改訂対象とする。
互換性は外周のアダプターと移行時のID対応で扱う。新しい内部モデルの制約にしない。

意味的な正本はscene、根拠は不変、現在の意味はResolver、検索は再構築可能な投影、
永続状態は関係モデルという既存ADRを継承する。基本的な原本登録・閲覧は
詳細解析を待たない。原本の同一性とsceneの同一性は別々に扱う。

性能は表の数ではなく、読む行数・読むバイト数・書換え回数・索引サイズ・
同時実行量で判断する。正規化する領域と、読み取り用にまとめる領域を明確にする。

## 2. 責務別の関係モデル

以下の名前は論理名であり、最終DDLや既存表の改名指示ではない。

| 領域 | 主な関係 | 所有する事実と境界 |
|---|---|---|
| 原本 | blob、blob_location | SHA256・バイト数による内容同一性と、複数の保存場所・可用性を分離 |
| メディア | asset、asset_source、derivative | 原本への参照、媒体属性、由来、生成版付き派生物。派生バイトを一覧行に置かない |
| 作品 | collection、collection_entry | entry固有ID、作品内順序、asset参照。同じassetの複数entryを許す |
| 意味 | scene、entity、assetとsceneの対応 | 視覚内容の意味。同一原本という理由だけで別sceneを自動統合しない |
| 根拠 | producer、producer_version、observationと型別詳細 | 判定元・モデル版をID参照し、不変の入力と訂正・取消参照を保持 |
| 解決 | resolver_version、resolutionと受理根拠の対応 | 対象の根拠世代に対する解決結果と追跡可能な根拠集合 |
| 検索 | media_current、tag、media_tag_current、collection_entry_current | 現在の一覧属性、タグ集合、順序。狭い索引付きの再構築可能な投影 |
| 作業 | operation、work_item、attempt、receipt | 利用者の依頼、処理単位、試行履歴、確定成果物への受領記録を分離 |

内部の大量参照には整数IDを使う。公開・交換の安定IDは別列に持つ。
ハッシュ・名称・URL・モデル識別文字列を全関連行へ繰り返さない。
自然キーの一意性と内部IDの主キーを分け、名前変更が巨大な関連更新にならないようにする。
根拠には対象・判定元版・根拠種別・日時を持ち、訂正は追記する。

blobとlocationの分離により、外付けディスク切断を内容の不存在と混同しない。
派生物は入力blob、用途、変換器版、パラメータの識別子で再生成可能にし、
原本と別の容量予算を持つ。最初はローカルファイル保存を実装対象にする。

作品内順序には全順序を持たせる。挿入用の疎な順序キーとentry IDの組を候補とし、
キー枯渇時の局所的な再配置コストを測る。全ページを毎回振り直す方式は既定にしない。
同じassetを2回置けることと、同じ投入の再送でentryが増えないことを別制約で保証する。

## 3. 一覧のための読み取り構造

一覧40件はmedia_currentから狭い行を取得する。原本、派生バイト、全根拠、
作品全体、全履歴を結合しない。タグ表示等は選ばれた40件へ上限付きで追加取得する。
安全性や削除状態など、表示可否を決める情報は必須のゲートとして扱う。

通常・セーフの代表的な並び順ごとに、絞り込みと順序を満たす索引を設計する。
たとえばセーフ＋公開可能の部分索引と安定ソートキーの組を候補とする。
すべての検索条件の組合せに索引を増設せず、複合タグでは選択性の高い候補から
整数ID集合を絞り込む。実行計画と分布の偏りで検証する。

連続ページ送りはソート値＋IDのカーソルを使い、閲覧済み件数に比例したOFFSETを避ける。
ソートキーのNULL順、昇降順、検索条件、セーフ条件、投影世代をカーソル契約に含める。
任意位置ジャンプは別設計とし、結果スナップショットや疎な位置索引の容量・構築費を比較する。
並行更新中の閲覧と、書き出しの固定スナップショットは保証範囲を分ける。

正確な全件数・全容量は通常一覧の同期処理から外す。集計は世代・更新時刻・
概算／確定を返す。特定検索の正確な件数が必要なときだけ、別の上限付き処理で求める。
検索エンジンや別DBは最初から追加せず、PostgreSQLでの実測が必要性を示してから検討する。

### 3.1 表示経路をコンパクトにする契約

正本と制約で状態を表し、画面ごとの推測・補正・再集計を減らす。
これは新しい投影表の数を増やす方針ではない。同じ値を所有する表・更新経路を
複数作らず、必要な読み取りと更新の仕事量から最小の構造を選ぶ。

最初の置換単位はタグ一覧と代表画像とする。現alphaの`tag_usage`を集計の
唯一の投影として拡張する案を検証し、別の同義の件数表は追加しない。
タグ名・別名は辞書が所有し、根拠は履歴、現在の所属は`label_head`が所有する。
集計はこれらから再構築でき、独立した正本として手修正しない。

| 読み取り項目 | 定義と整えるタイミング |
|---|---|
| タグ件数 | 正の現在タグを持つasset数。同じassetの作品内の重複出現では増えない。所属の実際の差分で更新し、同じ受付の再送では加算しない |
| タグ容量 | 同じ集合のblobバイト数をassetごとに一度数える論理容量。共有blobの物理占有・外付けへの複製容量とは分ける。導入は書込み増幅を測って決める |
| 代表画像 | 同じ所有者・正のタグ所属・表示可能なassetへの参照。原本や画像バイトは集計行へ複製しない。表示時には候補を探さず参照を読む |
| 反映状態 | 更新版と代表選択の方針版を識別する。未選択・再選択待ち・利用可能を区別し、未選択時は空の画像枠を返す |

代表画像は有効なものを安定して保持する。所属解除・削除・安全性変更等で
無効になれば、その参照を同じ更新で失効させ、再選択の要求を失わずに記録する。
安全性と所有者のゲートは常に表示時にも守る。候補選択は索引と処理上限を持ち、
通常画面は選択完了を待たない。カラー優先・ページ内の画像重複回避を、
全メンバー走査や複雑な全体制約が必要な必須条件にはしない。

任意の複合検索・除外条件・安全性条件の全組合せを事前集計しない。
タグ単体の集計を複合検索の正確な件数として転用しない。必要な正確な集計は
別の上限付き操作に分け、通常ページはカーソルによる取得を共通契約にする。
現行の「単一タグで5万件以上なら別計算」等の条件分岐を新モデルへ持ち込まない。

UI・MCP・取り込み・復元は同じ変更サービスを使う。小さな変更では所属と集計を
同一トランザクションで更新する。バルク処理でもその規則を共有し、行ごとの
トリガや画面側の補正を追加しない。再送・競合・巻き戻し・削除時の不変条件を
先に固定し、増分更新を正本からの全再計算と照合する。

置換の完了条件には、速さだけでなく削除できた旧コードを含める。
タグ一覧の同期画像探索、画面別の件数補正、再送の二重加算回避を個別に実装する
経路を、新しい共通経路へ置き換える。現行用の暫定アダプターは外周に限定し、
撤去条件と残存利用箇所を記録する。障害時の明示的な再構築・再試行は残し、
空結果や古い値を返すことで異常を隠さない。

v1.236.0で[タグ集計と代表画像の最小実装](../notes/collector-tag-summary.md)を追加した。
新ライブラリの集計・UI/MCP・復元経路が対象で、旧ライブラリの移行完了ではない。

## 4. 更新のための構造

根拠の書込み、解決、検索投影の更新は異なる責務とする。変更集合から影響対象を
重複除去し、対象ごと・バッチごとに解決する。タグ1行ごとのトリガで
同じ画像の全タグを何度も集計しない。根拠が増えた対象だけを処理する。

小さい手動編集は同期の限定的な解決・投影更新で即座に反映できる経路を設ける。
大量処理は非同期にまとめ、受付と投影反映を分けて返す。
どちらも同じResolver・根拠契約を通し、人間専用の別正本を作らない。
Resolverの計算量・対象履歴量・同時実行は予算化し、全履歴を毎回再走査しない
増分方式を、全再計算との一致で検証する。

投影は対象の根拠世代とResolver版を持つ。古いworkerの結果を比較更新で拒否し、
選択した世代をトランザクションで公開する。必要な再構築を失わないよう、
根拠のコミットと再処理要求は同一DBトランザクションで記録する。
全体再構築では旧投影を読みながら新世代を作り、照合後に切り替える。
一時的な二重容量と再構築I/Oも最低構成の予算に含める。

安全性の変更・権限取消・削除は古い投影やキャッシュが表示を広げないようにする。
失効世代を即座に確認するゲート、または同期投影更新を採用し、通常タグの
遅延更新と同じ整合性で扱わない。キャッシュキーだけで認可を代用しない。

## 5. 作業とUI/MCP

operationが取り込み・書き出し・取得の利用者意図を保持し、work_itemが対象単位の
状態とリース、attemptが試行履歴、receiptが確定結果を保持する。
頻繁なheartbeatで巨大な依頼本文や履歴を更新しない。親進捗は全子を毎poll集計せず、
状態遷移に対応する集計を保ち、受領記録から定期照合できるようにする。

再送は同じoperation／itemへ収束する。受付・列挙・原本受領・派生処理を区別する。
再試行予算、優先度継承、親単位の公平性、quota待機を共通スケジューラーが扱う。
既存の取り込みキューの状態値やタグ形式からこの内部契約を導出しない。

UIとMCPは共通のユースケースサービスを呼ぶ。取得元固有処理はアダプターに閉じる。
CPU解析を無効にしても、コピー・ハッシュ検証・手動整理・閲覧・書き出しは動く。
単一プロセス／少数workerから動かせる構成を優先し、分散基盤を基本利用の条件にしない。
ブラウザは検索世代付きキャッシュ、上限付き画像保持、古い応答の取消で同じ予算を守る。

## 6. 設計を選ぶ評価基準

| 操作 | 目標とする仕事量・比較項目 |
|---|---|
| 通常・セーフの40件 | 基本経路は索引探索＋返却候補中心。除外行数・heap読取・API時間を測る |
| 深い連続閲覧 | OFFSET位置に比例した走査を避ける。浅い位置と深い位置で比較 |
| タグ変更 | 根拠は変更件数に応じて追記。投影は変更対象単位で更新し、トリガ呼出し回数を測る |
| 一覧を開く | 履歴量・blob総容量の増加に伴う読取バイトの増加を抑える |
| 順序挿入 | 全作品書換えを避け、局所再配置時の最悪値も測る |
| 再試行 | 未受領item中心。同じ原本・位置の処理を無制限に繰り返さない |
| 定常運用 | 索引・WAL・VACUUM・再構築の負担を含め、4コア／8GiB案で検証 |

これは計算量の設計目標であり、任意の複合検索で走査一定を保証するものではない。
現行構造と目標構造を同じコーパスで比較し、p50／p95／p99、容量、書込み増幅、
中断回復を記録する。AI根拠が増えるケースと手動整理だけのケースを分ける。

## 7. 既存設計との解決課題

- `database/schema.sql` の `collection_asset` は(collection_id, asset_id)主キー。
  entry単位の同一性・複数出現を表せる構造へ改訂する。
- 同ファイルのobservation.producer_refとtag_projection.tagは文字列。
  producer版・tagの整数参照と、旧データの意味を保つ辞書化を設計する。
- 同ファイルのblobは保存先を1組で保持する。内容と複数locationの分離を設計する。
- assetとsceneの対応は、未解析メディアや動画・複数場面を扱う契約を確定する。
  仮sceneを作るだけで意味解決済みと扱わない。既存volume／DDLとの変更点を明記する。
- 手動入力を既存Volume 5の観測契約へ接続する型と、原本のみの移行経路を定義する。

本書はこれらのDDLを適用しない。詳細設計時に既存volume、ADR、schemaの
不一致を同じ変更で整合させる。既存設計の存在だけを採用理由にしない。

## 8. 実装と移行を分ける

まず隔離DBで目標モデルの最小経路を実装する。原本登録→根拠→解決→検索→
作品順序→書き出しの縦断を作り、現行と比較する。本番への移行前に構造の効果を測る。

移行は旧IDと新IDの対応、原本ハッシュ、根拠件数と訂正参照、作品内位置を照合する。
大容量データは再開可能なバッチで移し、追随差分はウォーターマークを持つ。
無期限の二重書込みは採用しない。切替時のwriterを一つにし、旧データは検収まで保全する。
切替後の更新を含む復旧手順を実証してから本番切替へ進む。
