# Kura — 個人コレクター向け製品仕様

- **Status:** Draft / 提案仕様。実装完了・性能達成・出荷保証を意味しない。
- **Version:** 0.1.0
- **Date:** 2026-10-17
- **Scope:** 個人の画像・動画アーカイブ、UI/MCP共通操作、低性能PC向けの実行・データ設計。

## 1. 製品の目的

長年集めて散在した画像・動画を、原本を保全したまま取り込み、重複を整理し、
タグや作品単位のまとまりで検索・閲覧できる個人用アーカイブにする。
専門道具としての正確さと制御性を備え、日常操作のコントロールは絞る。

主要な利用者は個人コレクター。既存コレクションの整理と再発見を第一の価値とする。
生成・学習・高度な所見解析は既存設計の発展先として維持するが、インストール、
原本登録、手動整理、検索、閲覧の利用条件にしない。GPUは基本機能の必須要件にしない。

## 2. 既存仕様との関係

本書は[既存8巻](./README.md)に不足する製品の利用体験と性能契約を補う草案であり、
別の正本スキーマを新設する文書ではない。[Volume 2](./volume-02-database.md)と
[ADR-0001](../adr/ADR-0001-immutable-observations.md)・
[ADR-0002](../adr/ADR-0002-relational-persistence.md)を含む既存の規範を、
この文書だけで取り消したり上書きしたりしない。衝突は設計課題として解決する。

- 原本・保存場所はメディア管理上の事実。sceneは既存仕様の意味的な正本であり、同一概念に混ぜない。
- 手動タグとモデルの出力は出所を持つ入力根拠として保存する。検索する現在タグは投影とする。
- 詳細解析が未実施・意味が未解決でも、原本の登録、メディア閲覧、根拠付きタグ整理は利用可能とする。
- 閲覧やMCP検索のたびに、全履歴のResolver実行や詳細解析を要求しない。
- `database/schema.sql`、その移行群、現在の本番 `public` スキーマを区別する。
  設計ファイルの存在を、現行アプリへの適用済みの証拠にしない。

## 3. 人向けUI

### 3.1 取り込み

1. ファイル・フォルダをライブラリへドロップ、またはファイル選択から指定する。
2. 取り込み前に対象、保存先、管理方法、判明している容量を確認できる。
3. 実行後は同じ画面で進捗、現在の段階、要対応項目を確認できる。
4. 取り込めたメディアは、全件のタグ付けが終わる前から閲覧・整理できる。

管理方法は「ライブラリへコピー」を既定とし、元ファイルを変更・移動・削除しない。
「元の場所を参照」も提供可能とし、選択時に外付けディスクの取り外しやパス変更の影響を示す。
ライブラリ本体とメタデータ・キャッシュの保存先は分離できる。HDD上の原本とSSD上の索引を扱える。
参照切れは原本消失と断定せず、再接続・場所の再指定で回復できる。

コピーは原本のバイト同一性を検証してから登録完了とする。サムネイル生成やタグ付けの失敗と、
原本登録の成否を別々に記録する。同じ原本の再投入は冪等に扱い、必要な作品所属や由来は追加できる。
完全重複と類似画像を分け、類似判定だけで原本を削除・置換しない。

### 3.2 検索・整理・閲覧

- 人はタグ、作者、作品、シリーズ、媒体種別などで絞り込める。内部テーブルや処理方式を覚える必要はない。
- 個別操作と一括操作で、タグ・所属・順序・原本保全の規則を共通にする。
- 設定を保持した「戻る」は、直前の一覧・対象・位置を即座に復元し、必要な更新を後から行う。
- キャッシュの識別には検索条件、並び順、セーフ設定、表示対象に影響する条件を含める。
  別条件の結果を混ぜず、取り消された古い応答で新しい画面を上書きしない。
- 漫画ビューは、予算内に保持した読み込み済みページへ戻る際、その画像を再利用する。
  作品全体を無制限に展開せず、保持数と展開後の画素量を両方制限する。
- 非フォーカス画像の暗転はオプションとし、既定はオフにする。
- 操作後に待つ場合は「読み込み中」「切り替え中」等を示す。失敗・待機・実行中を空白だけで表現しない。

### 3.3 書き出し

選択したメディア、作品、検索結果、ライブラリ全体から書き出せる。
既定は原本を書き出し、閲覧用の軽量版は明示的に選ぶ。タグ・作品所属・順序・元の名前・
出所と原本ハッシュを、移行可能なメタデータとして付属できる。

出力マニフェストのJSON等は交換形式・スナップショットであり、DBの正本を置き換えない。
同名ファイルを黙って上書きせず、部分成功、失敗、再開位置を示す。
再インポートで原本の同一性、タグの出所、作品所属と順序を検証できる形式にする。
暗黙の重複除外によって作品内の複数ページ位置を失わない。

## 4. Agent向けMCP

人向けUIとMCPは、共通のアプリケーションサービス、権限、検証、ジョブ管理を使う。
MCPを独立したDB書き込み経路や、別仕様の重複整理エンジンにしない。

最低限の能力群は次とする。具体的なツール名・引数は別途インターフェース仕様で固定する。

| 能力 | 契約 |
|---|---|
| 検索・取得 | 上限付きページ取得、安定した順序、媒体と作品の取得 |
| 取り込み | 対象の確認、実行、同じ要求の冪等な再送 |
| 整理 | 出所付きタグ変更、作品所属・順序の更新、類似候補の確認 |
| 書き出し | 対象・出力の計画、実行、結果と失敗の取得 |
| ジョブ管理 | 状況、進捗、待機理由、一時停止・再開・取消 |

長時間操作は永続ジョブIDを返し、接続を保持して完了を待つことを要求しない。
返答には処理件数、未処理、失敗、次に可能な操作を機械可読で含める。
取消は原本削除と同義にしない。破壊的操作は通常の整理操作と分け、権限と対象を明示する。
人が開始した処理をagentが状況確認し、agentが開始した処理を人がUIで確認・管理できる。

## 5. 共通ジョブと整合性

- 取り込み・書き出し・派生生成・タグ付けは、個別の成否と共通の親ジョブを持てる。
- 実行中、待機中、一時停止、要対応、成功、部分成功、取消を区別する。
- 探索済み・ハッシュ確認済み・原本登録済み・派生生成済みを区別する。
  総件数が未確定の間は、誤った0件・100%を出さない。
- 再起動・通信断から再開できる。完了記録と登録結果が食い違ったまま成功扱いにしない。
- 再試行は回数・待ち時間を制限し、同じ仕事のジョブIDを作り直して制限を回避しない。
- 新規の手動操作を、進捗のないバックグラウンド再試行より優先する。
- 更新の出所、処理版、対象を保持する。正本と検索投影の世代差を検出できる。
- UI/MCP双方から、同じジョブと同じ確定結果を参照する。

## 6. 低性能PC向けデータ・実行設計

### 6.1 読み取りの仕事量

- 現在の一覧・現在タグ・作品内順序を、正本と出所の履歴から再構築可能な、索引付きの読み取り用データとして保持する。
- 一覧40件の応答に、原本、配信用バイナリ、全作品、全所見、モデル重みを読み込まない。
- 連続閲覧は、飛ばす件数に比例して走査するOFFSETだけに依存しない。
  任意位置への移動は、順序と検索結果の世代を識別する位置情報等で別途設計する。
- 順序はID等のタイブレークを含む全順序とし、一覧・位置計算・漫画ビューで一致させる。
- 正確な全件数や容量を、毎回の40件取得の前提にしない。集計の世代・確定状況を示す。
- セーフ設定、状態、作品内順序、タグ検索など、製品の主要操作に対応する索引を設計・検証する。

### 6.2 保存・更新の仕事量

- 原本のバイト同一性をSHA256等で表し、ファイル名・MD5・類似度だけで代用しない。
- 原本と再生成可能な派生物を区別する。派生物は容量上限・退避・再構築の方針を持つ。
- サムネイル・閲覧用派生のWebP化を許容する。原本を置換せず、原本ハッシュと元形式を保持する。派生の寸法・画素量・変換CPU・キャッシュ容量も性能検証の対象とし、WebP化だけで性能保証の達成とは扱わない。
- DB外のバイナリ保存は既存blob設計と整合させ、DBの場所情報・生成版・整合性検証と結ぶ。
  バイナリを外へ出すだけで一覧が速くなるとは仮定しない。
- 繰り返す判定元・モデル・タグは安定IDで参照する。長い名前を大量の関連行の主キーへ繰り返し格納しない。
- タグ一括変更では、変更1行ごとに同じ画像の全タグを再集計しない。
  変更集合をまとめ、必要な投影を画像単位で更新する。出所の根拠は失わない。
- 現在状態、履歴、ジョブの頻繁な更新を分け、閲覧に履歴量が直接影響しない構造にする。
- 索引は対象クエリと対応付ける。利用統計の0だけを理由に一意制約の索引を削除しない。

### 6.3 実行予算

- 基本機能をCPUで利用できる。AI解析を無効化・延期しても原本登録、手動整理、検索、閲覧、書き出しは動作する。
- 取り込み、タグ付け、派生生成の同時実行数を制限し、対話操作にCPU・メモリ・DB接続の余裕を残す。
- ブラウザの描画要素、保持ページ、展開後の画像画素量、リクエスト同時数、メモリキャッシュに上限を持つ。
- 推奨構成から最低構成へ、CPU・メモリ・I/Oの強さだけで同じ設定を横滑りさせない。

## 7. 暫定性能契約と検収

以下は設計・比較のための**未検証の暫定目標**。実測を経て確定し、未達を達成済み・保証済みと宣伝しない。

参照環境案はCPU 4コア、RAM 8GiB、GPUなし、メタデータと派生キャッシュはSSD。
原本HDD・外付け切断時も別プロファイルで検証し、SSDと同じメディア表示時間は保証しない。
OS、ブラウザ、CPU型式、SSD型式、DB設定、アプリ版を測定記録に含める。

| 操作 | 暫定目標 |
|---|---|
| 待ち状態の可視化 | 操作から100ms以内に状態表示 |
| 一覧40件のメタデータ取得 | 10万件でp95 300ms以下、100万件でp95 500ms以下（暖機後） |
| 同条件のキャッシュ済み一覧へ戻る | 200ms以内に対象と位置を復元。同期の全件再取得を要求しない |
| 保持済み漫画ページへ戻る | 100ms以内に既存の表示可能画像を再利用 |
| 40件のサムネイル表示 | SSD・暖機後の参照コーパスでp95 1秒以下 |

10万件・100万件、疎なタグ・頻出タグ・複合タグ、画像・動画混在、セーフON/OFF、
大きい作品、似た画像、同じファイルの再投入を検査する。コーパスにはタグ数分布、
判定元数、履歴量、ファイルサイズ、画素数、動画比率、サムネイル条件を固定する。
メタデータSQL、API、DOM復元、画像の実表示の時間を混同しない。

冷えたキャッシュ、取り込み並行中、AI解析並行中も測定し、p50/p95/p99とCPU・メモリ・
ディスクI/O、DB/WAL・索引の増分を記録する。エラーを成功時間の集計から黙って除外しない。
単発の本番SQL測定だけで最低性能構成の達成とはしない。

原本ハッシュ、出所、手動修正、作品所属と順序が、取り込み中断・再開・書き出し・
再取り込みを通して保全されることも合格条件とする。

## 8. 現状との差分と実装順

2026-10-17の本番読み取り調査では、`public` に87テーブル、DBは約228GiB。
`post` は約147GiB（うちTOAST約143GiB）、判定根拠の `post_tag_actor_claim` は約67GiB。
後者の判定元文字列はサンプルで平均約250バイト。これらはその時点の物理容量であり、
全てが毎回の一覧取得で読まれるという意味ではなく、必要容量の予測値でもない。

代表SQLの暖機後単発測定は、通常の40件取得約1.4ms、セーフ40件取得約783ms。
後者では約68.8万件を条件不一致で除外した。20万件OFFSETでは200,040件を処理して40件を返した。
API全体や最低構成のベンチマークではない。

1. 原本保全と共通操作の契約を基に、[目標構造](./collector-target-architecture.md)を設計する。
2. 新しい関係モデル・検索投影・集合更新を隔離環境で縦断実装する。
3. 最低構成で現行と比較し、走査量・容量・書込み増幅・中断回復から構造を選ぶ。
4. UIのドロップ操作とMCPを同じサービスへ接続し、原本と根拠の往復を検収する。
5. 既存データの対応・差分追随・切替と復旧を独立した移行工程で実証する。

移行は既存の原本同一性・参照ID・タグ根拠・作品所属・順序を保つ。
旧API利用者との互換範囲、データ照合、再開、バックアップからの復旧を移行計画に含める。
本書の追加はDB移行や実装の着手・完了を意味しない。

第1段階の具体化は[取り込み・書き出し契約](./collector-transfer-contract.md)、
実装単位と進捗は[改善ロードマップ](../notes/collector-improvement-roadmap.md)で管理する。

## 9. 要確定事項

- 最低サポートOS・ブラウザと、参照環境の具体的な機種・コーパス・並行負荷。
- 冷機・並行処理中の許容遅延、ディスク容量・WAL増加・メモリ上限の数値。
- 出力マニフェストの版と互換性、元の場所を参照する管理方法のサポート範囲。
- 既存scene/entity設計を保ちつつ、基本コレクター操作で必要になる最小の所見・解決・投影処理。
- 整理用の自由タグは[専用の根拠・投影](../notes/collector-labels.md)へ接続済み。
  内容を表す意味タグの手動入力と既存Volume 5の書込み契約の接続は、別途確定する。
